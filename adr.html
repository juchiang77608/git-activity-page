ADR-0001：本機蒐集、公開靜態切片

狀態：已接受　·　2026-09-10（依既有實作公開整理）

背景

需要同時做到兩件事：本機追蹤多個 git repo 的開發活動（含未推上遠端的私有專案），以及把「有在寫 code」的節奏公開成可瀏覽的頁面。

若把本機全端系統直接部署上線，會暴露 repo 清單、訊息與路徑。若只做純前端、資料全在瀏覽器，又無法穩定讀取本機多個 repo 的歷史。

決策

分成兩層，互不共用執行環境：

  1. 本機蒐集：單機全端工具（Vue 3 + FastAPI + SQLite）讀取本機 git 歷史並持久化。不部署到雲端，不對外提供 API。
  2. 公開切片：本站只放靜態頁與一份匯出檔，經 GitHub Pages 發布。

公開層不知道本機工具的目錄結構，也不在瀏覽器裡連回本機 API。

理由

  • 蒐集需要檔案系統與 git，適合留在本機。
  • 展示只需要日期次數與語言合計，不需要即時查詢。
  • 兩層切開後，公開內容的洩漏面固定為靜態檔，較容易審查。

後果

正面

  • 私有 repo 可以納入統計，卻不必出現在 GitHub。
  • 公開頁無伺服器、無登入、無對本機 API 的依賴。

負面

  • 數字不會自動更新；要另走離線匯出（見 ADR-0004）。
  • 訪客看不到本機工具本身，只能看到聚合結果。

替代方案

方案未採用原因
將本機 API 部署上線預設會帶出不該公開的欄位與路徑
GitHub 貢獻圖代替不含未推送的私有 repo
定期 CI 從本機資料庫拉取本機資料不在遠端，CI 也拿不到

ADR-0002：公開資料僅含聚合統計

狀態：已接受　·　2026-09-10（依既有實作公開整理）

背景

本機資料庫為了除錯與對帳，會保存比公開頁所需更多的欄位。若「整庫同步」或把查詢 API 接到這個網站，隱私邊界會變成預設全開。

需要一條明確規則：什麼可以離開本機，什麼不行。

決策

離開本機、進入本站的資料只准以下形狀：

  • 每日 commit 次數：日期 → 整數
  • 語言檔案觸及次數：全域合計，以及依年合計
  • 匯出時間與總筆數

明確排除：repo 名稱、檔案路徑、commit 訊息、作者、diff 行數、原始副檔名。

匯出時以白名單欄位寫檔；多出來的欄位直接拒絕寫入。

理由

  • 熱力圖與語言條只需要次數，不需要識別單一 repo 或檔案。
  • 聚合之後，無法還原「哪一天改了哪個客戶專案」。
  • 規則寫在匯出層，比事後從頁面上藏欄位可靠。

後果

正面

  • 公開檔可用肉眼審查：不該出現路徑或 repo 名稱。
  • 頁面可以誠實說明資料範圍。

負面

  • 無法做「依 repo 篩選」或「點格子看 commit 列表」這類展示。
  • 次數含私有與公開 repo，外人無法核對單日細節——這是刻意的。

替代方案

方案未採用原因
公開 repo 清單、隱藏訊息清單本身已足以對應客戶／雇主專案
只統計已推上 GitHub 的 repo失去追蹤本機活動的目的
匿名化 repo 名數量與活躍度仍可能被對上已知專案

ADR-0003：語言 allowlist，不公開路徑

狀態：已接受　·　2026-09-10（依既有實作公開整理）

背景

語言分佈對了解技術節奏有用，但依副檔名統計很容易把路徑或少見檔名帶進公開資料（例如未知副檔名，或誤把路徑當成語言名）。

決策

  1. 本機同步時只保存語言顯示名 → 檔案觸及次數，不存路徑。
  2. 公開匯出再套一層 allowlist（TypeScript、Python、Vue 等已知語言名）。不在名單內的直接丟棄。
  3. 名稱還需通過安全字元檢查：拒絕路徑分隔符與 ..。
  4. 公開頁只呈現語言名與次數，不呈現副檔名。

本站與本機蒐集端使用同一組語言名，避免一邊寫了、公開頁卻讀不到。

理由

  • Allowlist 比「刪掉看起來像路徑的字」少漏網。
  • 未知副檔名若原樣輸出，等於洩漏專案慣用的內部檔型。
  • 次數以「檔案觸及」計，不需要（也不該）帶路徑才能加總。

後果

正面

  • 語言名稱可預期、可審查。
  • 熱力圖切換年份時，語言條可安全跟著變。

負面

  • 名單外的語言不會出現（例如冷門副檔名）。
  • 兩邊名單若沒同步，匯出會默默丟棄，統計略偏低。

替代方案

方案未採用原因
公開原始副檔名可能洩漏內部工具鏈或產生器檔
用 repo 名稱猜語言多語言 repo 會嚴重失真
只統計本站這個 repo不含本機其他專案

ADR-0004：離線匯出、手動發布

狀態：已接受　·　2026-09-10（依既有實作公開整理）

背景

本機資料庫與公開頁必須保持斷開（見 ADR-0001）。若這站的程式去打本機 API，一般訪客會連不到；若把本機服務開到網路上，又違反「API 不對外」的前提。

仍需要一條更新公開數字的路。

決策

  1. 在本機、離線讀取資料庫（唯讀），寫出公開用的 JSON。
  2. 人工檢查後再發布靜態檔。
  3. 公開頁只讀那一份 JSON，無其他後端、無定時爬蟲。
  4. 含本機絕對路徑的操作指令不寫進公開說明。

理由

  • 更新頻率低（人為「發布一版統計」），不值得做常駐同步。
  • 每次發布都經過版本紀錄，公開檔可對照、可回溯。
  • 靜態讀檔讓本機預覽與線上行為一致。

後果

正面

  • 公開站零營運：無常駐程序、無密鑰、無可被呼叫的 API。
  • 匯出失敗不會自動污染線上檔。

負面

  • 熱力圖會過期，直到下次手動匯出。
  • 忘記更新時，訪客看到的是舊節奏。

替代方案

方案未採用原因
公開頁直連本機 API訪客連不到；也擴大攻擊面
用雲端排程自動匯出雲端拿不到本機資料庫
把資料庫放到雲端再讓排程讀等於把蒐集層搬上雲，偏離 local-first
